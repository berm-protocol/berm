# The pocket

**Canonical. R4.** The predecessor is at
[`historical/POCKET_R1_SUPERSEDED.md`](historical/POCKET_R1_SUPERSEDED.md) —
evidence only, never authority.

## The pocket is not an address

This is the sentence the previous version got wrong, and everything else follows
from it.

> **The pocket is a supporter's cumulative WETH entitlement inside the immutable
> Berm Distributor.** It is an accounting position, not a balance sitting at an
> address.

The EVM address is two other things, and neither of them is the pocket:

1. the **authority** allowed to decide when that entitlement is converted, and
2. the **destination** the launched token is delivered to afterwards.

WETH is never pushed out to an EOA first. Doing so would destroy
graduation-gating, supporter-chosen timing, the immutable operating-fee
treatment, the fixed-route conversion and the accounting reconciliation — all of
which are working product, not aspirations.

```
Bags fees
   ↓
immutable Berm Distributor
   ↓
cumulative virtual WETH pocket        ← this is the pocket
   ↓  verified graduation
supporter-authorized full-pocket fixed-route buyback
   ↓
launched token → the committed EVM destination
```

## Two execution identities, and the signed object says which

A supporter's **execution identity** is the EVM key that authorises the buyback
and receives the token. There are exactly two ways to have one, they are not
interchangeable, and **the enrollment event declares which applies**.

| | `derived_v1` — Path A | `bound_wallet_v1` — Path B |
|---|---|---|
| Arrives with | nothing | an npub they already use |
| Nostr key | generated by us, parity-normalised **before persistence** | theirs, untouched |
| EVM key | the **same normalised secret** | an ordinary wallet they supply |
| Proof required | control of the derived address, by that secret | control of the supplied wallet |
| Never | — | **never derived from their npub** |

The mode is inside the signed event and inside the signed control message. A
reader cannot infer it, default it, or repair it. See
[`src/enrollment.ts`](src/enrollment.ts) and
[`ENROLLMENT-SPEC.md`](ENROLLMENT-SPEC.md) §2.

**Why the asymmetry.** Deriving an EVM address for someone who already has an
npub would name a destination they may never be able to open — they would have to
export an established identity key, work out BIP-340 parity, and import it into a
wallet. They already have a wallet. Ask for it.

## Path A — the derivation, and the one trap in it

```
d      = raw if y(raw·G) is even else (n − raw)    ← AT GENERATION, before persistence
xonly  = x-coordinate of d·G
npub   = bech32('npub', xonly)
addr   = keccak256(x ‖ y)[12:] of d·G, EIP-55
```

**Normalise before persistence, not at spend time.** If the raw key is stored and
a separate spending key derived later, the secret the user exports opens a
*different address* than the one displayed — plausible, fundable, and not theirs.
Nothing errors; it surfaces when they try to move money.

Negation does not change the npub, because x-only is the x coordinate and
negation preserves it. So this costs nothing and removes the trap entirely.

`vectors/pocket-address.json` is v2, covers both parity branches at generation,
and anchors on `secret key 1 → 0x7E5F4552091A69125d5DfCb7b8C2659029395Bdf` — the
canonical Ethereum address for that key, checkable against any Ethereum tool.

## The invariant that protects the money

> **No cohort root may commit an EVM destination unless control of that exact
> destination has been proven.**

Both modes require EVM control proof, and neither is exempt. In Path A the proof
demonstrates the normalisation actually happened. In Path B it demonstrates the
wallet is theirs rather than a string they pasted. Different question, same
evidence.

## Binding, rebinding, and the freeze

A destination may be replaced **before** the cohort root containing it is
finalised, by a new enrollment carrying valid proof for the new address. The
latest valid pre-finalisation binding is the one the roster uses.

**After finalisation the destination is frozen**, because it is inside the leaf
and the leaf is inside the root. Changing it would mean changing the root, which
is the thing that cannot happen. Do not describe the payout wallet as freely
replaceable anywhere.

## The backup, and what it is the exit from

NIP-49 `ncryptsec` — the secret encrypted under a passphrase with scrypt and
XChaCha20-Poly1305. Mandatory for Path A **before enrollment is complete**, and
the only place in the product where blocking a user is justified: someone who
leaves without it has an identity and an execution key that exist only in a
browser tab.

| | |
|---|---|
| KDF | scrypt, `r=8`, `p=1`, `log_n` **16** for browser-generated keys |
| Cipher | XChaCha20-Poly1305 |
| Key-security byte | **`0x00`** — a browser-generated key *was* handled insecurely, and that field exists to say so |
| Never | published to a relay |

For Path A this file is also the execution key, so the passphrase guards both the
identity and the buyback authority. Say that next to the field, not in a help
page.

Path B users need no such file from us. They already hold their signer and their
wallet, which is the point.

## What it costs, stated plainly

**Path A: to authorise a buyback the key has to reach a wallet.** That is a
deliberate step, and it happens when there is a reason to take it. Importing an
identity key into a wallet extension is a custody downgrade and the interface must
say so — sweep afterwards, or use a dedicated browser profile. Neither is perfect;
both beat silence.

**One key, two roles.** Losing it loses the identity and the execution authority
together, which moves `recovery/` and guardians from "eventually" to "before a
pocket holds anything real".

**And conversion depends on a market.** Website independence is not market
independence. If the committed route is unavailable the WETH entitlement remains
preserved in the Distributor — it is not lost, and it does not silently convert to
a direct withdrawal. `claimQuote()` is **not V1** and the open questions behind
that decision are recorded in [`SOVEREIGNTY.md`](SOVEREIGNTY.md).
