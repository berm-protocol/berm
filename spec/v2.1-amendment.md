# Berm v2.1 — Amendment

**Amends:** Berm v2.0 architecture specification
**Status:** Normative. Supersedes the named sections of v2.0.
**Nature:** Additive. No existing identity changes; no frozen test vector moves.

Key words **MUST**, **MUST NOT**, **SHOULD**, **MAY** are per RFC 2119.

Every change below came out of building against v2.0 and measuring things
rather than assuming them. Where a v2.0 statement was too strong, it is
corrected here explicitly rather than quietly.

---

## 1. Key wrapping — amends §3.2.2

### The flaw

v2.0 derives the identity key deterministically from PRF output:

```
sk = HKDF-SHA256(prf_out, "xnsb/v2/identity", "secp256k1|" || credential_id || "|" || i)
```

Since `prf_out` is credential-bound, **a second passkey produces a different
key — a second identity, not a backup.** There is no way to add a device.

Platform passkeys sync via iCloud Keychain and Google Password Manager, which
covers broken phones, new laptops and theft. It does not cover the case most
people actually live in: **an iPhone and a Windows PC.** Different ecosystems,
no sync, no shared identity.

### The amendment

The first credential stays deterministic. Additional credentials **wrap** the
same key.

```
credential #1   sk = HKDF(prf_out₁, …)                    ← unchanged, byte-identical
credential #2   wrapped₂ = AEAD(sk, kek₂)   kek₂ = HKDF(prf_out₂, "xnsb/v2/wrap", …)
credential #3   wrapped₃ = AEAD(sk, kek₃)
```

This is deliberately the best of both: credential #1 needs **no stored data at
all**, so the elegant "nothing to lose" property survives; every other device
works from a blob that cannot meaningfully be lost.

**Normative:**

- The wrapping AEAD **MUST** be AES-256-GCM with a 12-byte random nonce, or an
  equivalent authenticated cipher. Unauthenticated encryption **MUST NOT** be used.
- The KEK **MUST** be derived with a `wrap`-specific HKDF salt and info, so a
  wrapping key can never collide with an identity key.
- Wrapped blobs are ciphertext and **MAY** be replicated freely — signer origin,
  the user's node, a downloaded file, a relay. Replicate widely; losing one copy
  costs nothing.
- A wrapped blob **MUST** record `credential_id`, version, nonce, and ciphertext.
- Implementations **MUST NOT** derive a fresh identity when an unrecognised
  credential is presented. That silently forks the user in two. Offer to enrol
  the credential as an additional device instead.

### Blob format

```json
{
  "v": 1,
  "credential_id": "<hex>",
  "alg": "AES-256-GCM",
  "nonce": "<hex, 12 bytes>",
  "ct": "<hex, 48 bytes: 32-byte key + 16-byte tag>",
  "npub": "npub1…",
  "created_at": 1785000000
}
```

`npub` is included so a device can confirm it unwrapped the expected identity
before use. It is public and leaks nothing.

## 2. Recovery — new section

Two losses are routinely conflated. They are different problems.

### 2.1 Case A — X account gone, identity intact

**Nothing is recovered, because nothing was lost.** This is what the
architecture exists to deliver.

1. Post a fresh NIP-39 proof from the new X account
2. Archive it (§7)
3. Publish an updated kind 0: new claim in, dead claim **out**

Articles, follows and history are untouched — none of them ever depended on X.

**Removing the dead claim is normative, not cosmetic.** Abandoned handles are
re-registered, and a stale claim leaves a profile pointing at a stranger.
Clients **SHOULD** warn when a claim's handle no longer resolves.

### 2.2 Case B — identity lost

| Lost | Consequence | Recoverable |
|---|---|---|
| One device | none, if the passkey syncs | yes, automatically |
| Entire OS ecosystem | none, if a second credential is enrolled | yes, via §1 |
| All devices | identity | only from the §3.2.3 backup |
| All devices **and** backup | identity | **no** |

### 2.3 What a user must hold

Ranked by what it saves:

1. **One working authenticator** — covers device loss, X suspension, node death
2. **A second enrolled device** — covers losing an entire ecosystem account
3. **An encrypted keyfile and its passphrase** — covers losing everything

Nothing else is required. Articles return from relays, node pages re-render,
follow lists are held by other people. **The key is the only irreplaceable
thing**, which is why enrolment blocks until a backup exists.

## 3. Rotation and guardians — new section

### The honest limit

**On Nostr there is no account to recover.** The identity *is* the key.
Guardians cannot restore it. They can only **attest** that a new key is the same
person — social consensus, not cryptographic recovery. Whether it works depends
on relying parties choosing to honour it.

Implementations **MUST NOT** describe this as key recovery.

### 3.1 Pre-commitment

The strongest and cheapest action, taken **while the old key still works**:

```
kind 30078   d = berm:recovery:v1
├─ guardian  <npub>          (repeated, M-of-N)
├─ threshold 2
└─ anchored + archived
```

One signed event, published while healthy, worth far more than improvising
after a loss. Implementations **SHOULD** prompt for this at enrolment.

### 3.2 Rotation

```
kind 30078   d = berm:rotation:v1
├─ old-pubkey  <hex>
├─ new-pubkey  <hex>
├─ reason      lost-device | compromise | planned
└─ anchor      required
```

Signed by the old key where possible, and by guardians where not.

### 3.3 Resolution

A resolver **SHOULD** prefer `npub_new` when either holds:

- rotation is signed by `npub_old`, anchored **before** that key went dark, or
- signed by at least `threshold` guardians named in a pre-commitment that was
  itself anchored before the loss

A resolver **MUST NOT** honour a rotation whose anchor postdates a competing
claim it would displace. Otherwise a stolen key rotates away from its owner.

## 4. Node routing — amends §5, **bug fix**

v2.0's storage keys correctly on `(pubkey, d_tag)`, but lookup and routing use
the **handle**, which is mutable. Change a handle and every existing URL 404s
while the data sits intact.

**Normative:**

- Article resolution **MUST** be by `(pubkey, d_tag)`.
- Nodes **MUST** keep a handle history and **MUST** 301 superseded handles to
  the current one.
- `/@handle/slug` **MAY** remain the display URL; it **MUST NOT** be the lookup
  key.

## 5. X user ID — clarifies §3.3 and §5.2

v2.0 forbids persisting the raw X user ID. §5 of this amendment records it in
attestations. That is not a contradiction, and the distinction is load-bearing:

| Context | Rule | Why |
|---|---|---|
| Node session / database | **MUST NOT** persist raw; store `HMAC(site_secret, id)` | prevents a node quietly accumulating an X↔identity correlation table |
| Identity attestation | **SHOULD** publish the raw id | the user is deliberately publishing a claim about their own public account |

The difference is consent and purpose, not the datum. **Handles recycle; numeric
ids never do** — a claim bound only to a handle cannot distinguish the original
owner from whoever registers it next, which defeats the entire continuity story.

## 6. NIP-39 verifiability — corrects §3.4

v2.0 called the Channel A proof "third-party verifiable". **Too strong.**

- A **human** can click the link and read the post. True.
- A **machine** cannot verify at scale without X API access, which is now
  pay-per-use.
- If the account is deleted, the proof disappears — precisely when it is needed.

Corrected wording: Channel A is **human-verifiable, and machine-verifiable only
with API access**. Channel B (live `/2/users/me`) covers the automated path
node-side. §7 addresses the deletion problem.

## 7. Proof archiving — new, amends §3.4

A NIP-39 proof post **dies with the account**. The evidence for an identity
claim evaporates at the exact moment someone else holds the old handle and is
impersonating its former owner.

**Normative:**

- Implementations **MUST** offer archiving of the proof post at creation, and
  **SHOULD** make it the default path.
- The snapshot URL and capture time **MUST** be recorded in the identity
  attestation.
- A snapshot captured **before** the proof post was made **MUST NOT** be
  accepted. Old captures of the same URL are common, and attaching one is worse
  than attaching nothing because it looks valid.
- Resolvers **MUST** surface the absence of a snapshot as a caveat.

## 8. Timestamps — new

**`created_at` is author-asserted and is not evidence.** Any key can sign an
event dated 2009. Tooling that renders it as fact is how a squatter wins an
argument they should lose.

**Normative:**

- Priority between competing claims **MUST** derive from an external anchor
  (OpenTimestamps or equivalent), never from `created_at`.
- Unanchored claims **MUST NOT** outrank anchored ones.
- Where no claim is anchored, a resolver **MUST NOT** name a winner. Refusing to
  choose is the correct output.
- A resolver that cannot itself complete anchor verification **MUST** say so
  rather than implying it did. Pulling block headers from a public API would
  reintroduce a trusted third party into the one place that must not have one.

## 9. Node authorisation — amends §5.2, **bug fix**

v2.0's ingest requires an X OAuth session. That makes the entire node unusable
without X credentials — inverting the architecture, which exists so that X is
never load-bearing.

**Normative:**

- Ingest **MUST** authorise on a valid signature from an Berm identity.
- An X session **MUST NOT** be required for any operation.
- Nodes **MUST** be fully functional with the X settings left blank.
- X OAuth becomes an optional upgrade, buying `verified` instead of `claimed`
  and, where scoped, one-click Article drafting.

Handle linking requires **no API at all**: a share intent is a plain URL, and
the user pastes back the resulting post URL.

## 10. X Articles — amends §9.1

v2.0 states the framework never publishes programmatically to X. Read literally
that forbids an editor's Publish button, which was not the intent.

**Corrected boundary — human-in-the-loop, not "never touch the write endpoint":**

- **Permitted:** a person clicking Publish in an editor they are looking at,
  with their own OAuth consent. This is what `POST /2/articles/draft` exists for.
- **Prohibited:** unattended, bulk or scheduled posting with no human present;
  anything resembling paid engagement.

**SHOULD:** prefer creating a *draft* and letting the author press publish inside
X. Better fidelity, better consent, and a compliance posture that is
self-evident rather than argued.

## 11. Measured X paste behaviour — new

Measured against the live editor, replacing assumption:

| Element | Result |
|---|---|
| h1, h2, bold, italic, strike, links, lists, blockquote, long paragraphs, unicode | survive |
| h3 | demoted to body text — X has two heading levels |
| inline code, code blocks | flattened to plain text |
| **images — hosted URL and data URL alike** | **dropped entirely** |
| title field | **not populated**; the h1 lands in the body |

**Normative for exporters:**

- **MUST NOT** emit the h1 into the body; supply the title separately.
- **SHOULD** demote h3 to bold, so it still reads as a heading rather than
  dissolving into prose.
- **MUST** replace images with positional markers and present them separately
  for manual placement.
- **MUST** warn before the copy, not after. Losing things loudly beats losing
  them silently.

## 12. Archive attestations — new

X data archives are **unsigned JSON in a JavaScript wrapper**. X attests
nothing. Import therefore produces an **attested** claim, never a **verified**
one, and implementations **MUST NOT** use the word "verified" for it.

**Normative:**

- The OAuth account id **MUST** be compared against `account.js`; a mismatch
  **MUST** abort the import. This is what prevents importing someone else's
  archive.
- The archive **MUST** be hashed before parsing, and the hash pinned in the
  attestation.
- **`direct-messages.js` MUST NOT be imported, in any form, encrypted or
  otherwise.** It contains other people's words, and they never consented to
  publication on a permanent network. The exclusion **MUST** be stated in the UI.
- Bulk content **MUST NOT** be published as one event per post. Relays will
  rate-limit or ban, and event size caps make a single event impossible. Publish
  a signed manifest; keep bulk on the node.

## 13. Wayback capabilities — measured

| Endpoint | Result |
|---|---|
| `archive.org/wayback/available` | HTTP 200, `Access-Control-Allow-Origin: *` |
| `web.archive.org/save/<url>` | no CORS headers |

A browser **can** verify snapshots and **cannot** submit captures. The primary
path is therefore user-triggered — open the save URL, poll the CORS-open
availability API — and requires no credentials from anyone. Server-side capture
is an optional node upgrade.

**The Internet Archive MUST NOT be the sole durability layer.** It is one
US nonprofit under sustained legal and financial pressure. Durability is the
number of independent copies: local export, node cache, N relays, archive
snapshot.

## 14. Open questions

Recorded rather than guessed:

1. **X Articles entity shape.** The docs show `entities` as an array; standard
   DraftJS ContentState uses `entityMap` as an object. Unresolved — a harness
   exists to determine it empirically.
2. **Article API billing.** Post pricing is documented; whether Article
   endpoints bill identically is unconfirmed. Not to appear in user-facing copy
   until measured.
3. **Paste fidelity of the rich-text handoff** across browsers beyond the one
   tested.
4. **PRF availability** across the full platform matrix — the harness exists;
   real hardware results are pending.

## Conformance additions

- [ ] A second enrolled credential unwraps the **same** identity, never a new one
- [ ] An unrecognised credential offers enrolment; it never silently forks the user
- [ ] Article lookup resolves by pubkey; superseded handles 301
- [ ] Raw X user ids appear only in user-published attestations, never in node storage
- [ ] Proof posts are archived at creation; pre-dating snapshots are rejected
- [ ] Priority derives from anchors; unanchored claims never outrank anchored ones
- [ ] With no anchors present, no winner is named
- [ ] The node functions fully with X settings blank
- [ ] X exports omit the h1, demote h3, and mark images for manual placement
- [ ] Archive imports abort on account-id mismatch and never touch DMs
