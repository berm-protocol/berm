# Berm v2.0 — Architecture Specification

**Project:** Berm
**Home:** xonly.ai
**Status:** Normative. Downstream code is generated from this document, not guessed.
**License:** MIT
**Supersedes:** v1.0 (architecture blueprint) — **v1.0 is cryptographically broken and MUST NOT be implemented.** See §12.1.

Key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY** are per RFC 2119.

---

## 0. What changed and why

v1.0 derived the user's Nostr private key from their X user ID:

```
nsec = HKDF-SHA256(ikm = x_user_id, salt = "X-Nostr-Sovereign-Bridge-V1-Salt")
```

X user IDs are public. The salt is a literal in an open-source repository. Therefore the private key is a **public function of a public input** — computable by anyone, for anyone, in microseconds. HKDF stretches entropy; it does not create it. The construction has an effective security level of **zero bits**.

Second-order consequences, all fatal on their own:

| Consequence | Detail |
|---|---|
| Universal forgeability | Any observer derives any user's `nsec` from their public X ID. |
| No rotation | The key *is* the identity. Compromise is permanent; recovery requires abandoning the X account. |
| Node operators are omnipotent | The X ID passes through the WordPress node, so every site operator can derive every visitor's key and impersonate them **on every other site**. |
| PIN doesn't help | Attacker knows the X ID and the target `npub`, so brute-force is offline and unthrottled. 6 digits ≈ instant. |
| "Wipe JS variables" is not a control | JavaScript offers no memory-zeroing guarantee. |

The cross-site sameness that makes v1 attractive is precisely what makes it unfixable by scoping. **The derivation is removed entirely.**

v2.0 keeps every product property v1 promised except one — silent zero-click key materialisation at a brand-new origin — and replaces the broken primitive with hardware-bound key custody plus a publicly verifiable X↔Nostr binding.

---

## 1. Design axioms

1. **The key is never a function of a public value.** All identity key material originates from a CSPRNG or a hardware-bound PRF.
2. **X is an attestation, not a credential.** X proves *who the human claims to be*. It never proves, produces, or protects key material.
3. **Nodes are untrusted.** Any site running the plugin is assumed hostile. It MUST NOT be able to sign as the user, now or later.
4. **Custody lives at exactly one origin per user.** Cross-site identity requires a shared signer origin; WebAuthn credentials are RP-ID-scoped and cannot be shared across domains (§3.2.1).
5. **Every claim must be independently verifiable** by a third party with no privileged access — including reproducing the shipped bytes from source.
6. **Degradation is designed, not discovered.** X ban, signer outage, domain loss, relay loss each have a specified path (§8).
7. **No component depends on X's continued goodwill for correctness** — only for convenience.

## 2. Threat model

Explicitly in scope. A design decision that does not defend against a listed actor MUST be justified inline.

| # | Actor | Capability | Defended by |
|---|---|---|---|
| T1 | Curious node operator | Reads all server-side session data, all PHP memory | §5.2 — node never receives key material |
| T2 | Malicious node operator | Serves modified JS to its own visitors | §3.2.1 signer origin isolation, §6 SRI + reproducible builds |
| T3 | Public observer | Knows every user's X ID, handle, npub | §3 — no secret is derivable from public data |
| T4 | Relay operator | Sees all published events and connecting IPs | §4.5 NIP-44 for private payloads; relay diversity §4.4 |
| T5 | X (the platform) | Can revoke OAuth, ban accounts, change APIs | §8.1 — X is on the auth path, never the correctness path |
| T6 | Mass-reporter / impersonator | Registers lookalike X handles and npubs | §3.4 two-way binding, §3.5 NIP-05 anchor |
| T7 | Supply-chain attacker | Compromises npm dep, CDN, or release pipeline | §6 — no CDN, pinned deps, reproducible + signed releases |
| T8 | The Berm project itself | Hosts the default signer origin | §3.2.4 — signer cannot decrypt; self-hosting is first-class |

**Out of scope (stated, not hand-waved):** malware on the user's device with DOM access at the signer origin; a compromised authenticator; global passive network adversary performing traffic correlation across relays.

## 3. Identity architecture

### 3.1 Custody tiers

A conforming client MUST attempt tiers in this order and MUST NOT fall back to a lower-security tier silently.

| Tier | Mechanism | Trust in Berm | Target user |
|---|---|---|---|
| **0** | NIP-07 browser extension (Alby, nos2x, …) | **None** | Existing Nostr users |
| **1** | Berm Signer at a single origin, key derived via WebAuthn PRF | **Continuing control of the signer DNS name, indefinitely** (§3.2.4, §3.2.5) | Mass market — the default |
| **2** | Any NIP-46 remote signer / bunker (self-hosted, Amber, nsec.app) | None | Sovereignty maximalists |

Tier 1 is the on-ramp. Tiers 0 and 2 are the exits. **The protocol MUST remain fully functional if the Tier 1 signer disappears permanently.**

**Tier 1 is NOT sovereign, and MUST NOT be presented as though it were.** The protocol is sovereign; this tier trades that property for onboarding reach, deliberately and temporarily. Earlier revisions of this document and of the user-facing documentation described the three tiers as differing only in friction. That was false, and §3.2.5 states why.

### 3.2 Tier 1 — the Berm Signer

#### 3.2.1 Why a single origin is structurally required

WebAuthn credentials are bound to a Relying Party ID, which is a registered domain. A passkey created at `blog-a.com` is unusable at `blog-b.com` — by design, and this is not circumventable. A per-site passkey therefore yields a *per-site identity*, which defeats the entire premise.

Therefore: custody is centralised at **one origin**, and nodes reach it over **NIP-46**.

```
  ┌──────────────┐         ┌──────────────┐         ┌──────────────┐
  │  blog-a.com  │         │  blog-b.com  │         │  xonly.ai   │
  │  (WP node)   │         │  (WP node)   │         │  (WP node)   │
  └──────┬───────┘         └──────┬───────┘         └──────┬───────┘
         │                        │                        │
         │      NIP-46 signing requests (never keys)       │
         └────────────┬───────────┴────────────┬───────────┘
                      ▼                        ▼
          ┌───────────────────────┐   ┌────────────────────┐
          │  signer.xonly.ai     │   │  user's own bunker │
          │  (Tier 1, default)    │   │  (Tier 2)          │
          └───────────┬───────────┘   └────────────────────┘
                      │
                      ▼  WebAuthn PRF (never leaves device)
              ┌───────────────┐
              │ Authenticator │  ← platform passkey, synced by OS
              └───────────────┘
```

This is the single most important structural change from v1. It is what makes cross-site identity and key security simultaneously achievable.

#### 3.2.2 Key derivation (normative)

The signer derives the secp256k1 secret key from the WebAuthn PRF output. No ciphertext at rest, no seed phrase, no server-side secret.

```
prf_salt   := UTF8("xnsb/v2/prf/identity")            // fixed, public, per-purpose
prf_out    := WebAuthn PRF eval.first  (32 bytes, credential-bound, hardware-derived)

ikm        := prf_out
hkdf_salt  := UTF8("xnsb/v2/identity")
info(i)    := UTF8("secp256k1|") || credential_id || UTF8("|") || uint8(i)

sk_i       := HKDF-SHA256(ikm, hkdf_salt, info(i), 32)
```

**Scalar validation is mandatory and deterministic.** Accept `sk_i` iff `0 < int(sk_i) < n`, where

```
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
```

If invalid, increment `i` and re-derive. Start at `i = 0`. Implementations MUST NOT skip this check, MUST NOT clamp, and MUST NOT reduce mod `n`.

`prf_out` is 32 bytes of HMAC output computed inside the authenticator, bound to the credential and to `prf_salt`. It is not derivable from anything public. This is the entropy v1 lacked.

Reference implementation:

```ts
// @noble/hashes v2 is ESM-only: subpath imports REQUIRE the .js extension.
// 'sha256' was consolidated into 'sha2'. Both changes are mandatory — the v1
// forms ('@noble/hashes/sha256', extensionless paths) fail to resolve on v2.
import { hkdf } from '@noble/hashes/hkdf.js';
import { sha256 } from '@noble/hashes/sha2.js';
import { bytesToHex } from '@noble/hashes/utils.js';
import { getPublicKey, nip19 } from 'nostr-tools';

// Hardcoded, not read from the curve library. @noble/curves v2 removed
// `secp256k1.CURVE` (v2 equivalent: `secp256k1.Point.Fn.ORDER`); pinning the
// literal keeps this file version-proof and makes the test vector exact.
const N = 0xfffffffffffffffffffffffffffffffebaaedce6af48a03bbfd25e8cd0364141n;

const PRF_SALT = new TextEncoder().encode('xnsb/v2/prf/identity');
const HKDF_SALT = new TextEncoder().encode('xnsb/v2/identity');

/** Step 1 — obtain hardware-bound entropy. Runs ONLY at the signer origin. */
export async function evaluatePrf(credentialId: Uint8Array): Promise<Uint8Array> {
  const assertion = await navigator.credentials.get({
    publicKey: {
      challenge: crypto.getRandomValues(new Uint8Array(32)),
      allowCredentials: [{ id: credentialId, type: 'public-key' }],
      userVerification: 'required',
      // `eval` is valid here. When allowCredentials is non-empty, prefer
      // `evalByCredential: { [b64url(credentialId)]: { first: PRF_SALT } }`.
      // Note: evalByCredential MUST be empty if allowCredentials is empty,
      // or the call throws NotSupportedError.
      extensions: { prf: { eval: { first: PRF_SALT } } },
    },
  }) as PublicKeyCredential;

  const results = assertion.getClientExtensionResults() as any;
  if (!results?.prf?.results?.first) {
    throw new PrfUnsupportedError();   // caller MUST route to Tier 0 or Tier 2
  }
  return new Uint8Array(results.prf.results.first);   // 32 bytes
}

/** Step 2 — deterministic, validated reduction to a secp256k1 secret key. */
export function deriveSecretKey(prfOut: Uint8Array, credentialId: Uint8Array): Uint8Array {
  const enc = new TextEncoder();
  for (let i = 0; i < 256; i++) {
    const info = new Uint8Array([
      ...enc.encode('secp256k1|'), ...credentialId, ...enc.encode('|'), i,
    ]);
    const sk = hkdf(sha256, prfOut, HKDF_SALT, info, 32);   // length is in BYTES
    const v = BigInt('0x' + bytesToHex(sk));                // no Buffer in browsers
    if (v > 0n && v < N) return sk;                         // valid scalar
  }
  throw new Error('derivation exhausted');            // probability ~2^-2048
}

/**
 * nostr-tools v2 API asymmetry — get this wrong and it throws at runtime:
 *   getPublicKey(sk: Uint8Array) -> hex string
 *   nip19.nsecEncode(sk: Uint8Array)      <- BYTES
 *   nip19.npubEncode(pubkey: hex string)  <- HEX
 */
export function toIdentity(sk: Uint8Array) {
  const pkHex = getPublicKey(sk);
  return { pubkeyHex: pkHex, npub: nip19.npubEncode(pkHex), nsec: nip19.nsecEncode(sk) };
}
```

**Pinned dependency versions** (`SOURCES.lock`, §6): `nostr-tools ^2.24`, `@noble/hashes ^2.2`, `@noble/curves ^2.2`. A major bump to any of these invalidates §7 test vectors and MUST re-run them before merge.

#### 3.2.3 Enrolment and backup (normative)

PRF output is credential-bound: **lose the passkey, lose the identity.** Platform passkeys sync via iCloud Keychain / Google Password Manager, which covers device loss but not account loss.

Therefore, at enrolment the signer **MUST**, before the identity is usable:

1. Create the passkey with `residentKey: 'required'`, `userVerification: 'required'`, and `extensions: { prf: {} }` on `create()`.
2. Verify PRF actually returns a value on a subsequent `get()` — some authenticators advertise and fail. If it does not, abort and route to Tier 0 or Tier 2. **MUST NOT** proceed with a degraded derivation.
3. Present the `nsec` once, and require the user to complete **one** of: download an encrypted keyfile (Argon2id, ≥64 MiB memory cost, user passphrase), or confirm a written backup with a re-entry challenge.
4. Persist `{ credential_id, npub, created_at }` in the signer origin's local storage as the credential registry. Multiple credentials MAY be registered; each yields a distinct identity and the user MUST explicitly choose the active one.

#### 3.2.4 What the signer origin can and cannot do

- **Cannot** read `prf_out` without a live user-verified authenticator gesture.
- **Cannot** exfiltrate keys silently — the derivation is client-side and the origin ships no network calls in the signing path (enforced by CSP `connect-src` allowlist limited to relay WSS endpoints).
- **Can**, if compromised at the source-serving layer, serve malicious JS at the next page load. This is the residual Tier 1 risk *from a break-in*. It is mitigated, not eliminated, by §6, and it is the explicit reason Tiers 0 and 2 exist and are documented to end users in the UI, not buried in docs.

The larger exposure is not a break-in at all. See §3.2.5.

#### 3.2.5 The RP-ID dependency (normative disclosure)

**Threat T9.** WebAuthn binds every credential to a Relying Party ID derived from the signer origin. The authenticator releases `prf_out` to any page served under that RP ID and has no way to distinguish one operator from another. Therefore:

> Whoever controls the signer DNS name can obtain the identity key of every Tier 1 user who authenticates after the transfer.

This requires no compromise of any system. Domain lapse, expiry, sale, registrar action, UDRP transfer or a court order in any jurisdiction with reach over the registrar all produce the same result. §6's controls — CSP, SRI, reproducible builds, published hashes — defend the **bytes served under a name**. T9 is an attack on the **name**, and none of them apply to it.

Normative consequences:

1. A conforming implementation **MUST NOT** describe Tier 1 as sovereign, self-custodial, or trustless in end-user-facing copy, marketing, or documentation.
2. Tier 1 enrollment **MUST** complete the key export of §3.2.3 step 3 before the identity is used for anything the user would mind losing. Export guarantees the user cannot be *locked out*; it does **not** guarantee they remain the *only* signer. Implementations MUST NOT conflate the two.
3. An implementation that operates a signer origin **SHOULD** publish a build attestation (`berm:signer-build:v1`) signed by a key held offline, and **SHOULD** document the pubkey out of band, so that nodes running the signer gate refuse a name-holder who cannot produce a valid attestation. This protects users who arrive through a gated node; it does not protect users who navigate to the signer origin directly.
4. The registration for any production signer origin **SHOULD** be held with registrar lock and an expiry horizon materially longer than the project's planning horizon, and that expiry date **SHOULD** be published.

**Resolution path (v2.2, specified, not implemented).** Replace `prf_out` as the sole entropy source with a NIP-06 mnemonic root that the user holds, with the passkey acting as a wrapper over it (`sk = HKDF(prf_out ‖ argon2id(passphrase, salt), …)` or an equivalent construction requiring an input the name-holder cannot obtain). Until that ships, this section is the accurate statement of Tier 1's security, and §3.1 ranks the tiers correctly.

### 3.3 X OAuth — scoped role

The node performs standard OAuth 2.0 Authorization Code Flow with PKCE. Its output is used for **exactly two things**:

1. Rendering "signed in as @handle" in the node UI.
2. Producing a **live attestation** (§3.4, channel B).

Normative constraints:

- The X user ID **MUST NOT** be used as, mixed into, or influence any key derivation.
- The node **MUST NOT** persist the raw X user ID. If a local pseudonym is needed, store `HMAC-SHA256(site_secret, x_user_id)` truncated to 16 bytes.
- The X access token **MUST NOT** be sent to the browser and **MUST** be discarded after the `/2/users/me` call.
- Login **MUST** be completable without X at all (Tier 0 / Tier 2 direct entry).

### 3.4 X ↔ npub binding — two channels

**Channel A — public, permanent, third-party verifiable (NIP-39).**

The user posts a tweet — manually, via a share intent, no API automation — containing exactly:

```
Verifying my account on nostr My Public Key: "npub1..."
```

The tweet ID goes into the kind 0 `i` tag:

```json
["i", "twitter:dorian_handle", "1789456123456789012"]
```

Any Nostr client can verify by resolving `https://twitter.com/<handle>/status/<proof>`. This is the standard NIP-39 mechanism; Berm **MUST NOT** invent a custom tag for this purpose. (v1's `["x-identity", "12345678"]` and `"proof_verification_token"` are removed.)

**Channel B — live, node-local, zero-cost.**

At OAuth completion the node calls `/2/users/me`, obtains the authenticated handle and ID, and checks that the handle matches the one in the user's NIP-39 `i` tag. This catches handle transfers and stale claims that Channel A alone cannot. The result is a session-scoped boolean; it is **not** published.

**Reverse binding (SHOULD).** The user sets their X profile URL field or pinned post to `https://xonly.ai/p/<npub>`, closing the loop in the X→Nostr direction for humans who start on X.

A node **MUST** display three distinct badge states and never conflate them: `verified (A+B)`, `claimed (A only, unverified)`, `unlinked`.

### 3.5 NIP-05 anchor

Served from the domain, **not** the site root:

```
GET https://xonly.ai/.well-known/nostr.json?name=_
Access-Control-Allow-Origin: *
Content-Type: application/json
```

```json
{
  "names": {
    "_": "<project_root_pubkey_hex>",
    "signer": "<signer_service_pubkey_hex>"
  },
  "relays": {
    "<project_root_pubkey_hex>": ["wss://relay.damus.io", "wss://nos.lol", "wss://relay.primal.net"]
  }
}
```

`_` is the reserved name that renders as the bare domain. (v1 used `"root"` and the wrong path; both are corrected.) The file **MUST** be served with permissive CORS or clients will silently fail to verify.

### 3.6 Rotation and revocation

Because the key is no longer a function of the X ID, rotation is now possible and **MUST** be supported:

1. Derive a new identity from a new credential (§3.2.2, new `credential_id`).
2. Publish a kind 0 update from the **old** key containing an `["alt-pubkey", "<new_pubkey_hex>"]` tag and a plaintext migration note.
3. Publish kind 0 from the **new** key carrying the same NIP-39 `i` tag, re-proved with a fresh tweet.
4. Update `.well-known/nostr.json` if the rotating identity is a project key.

There is no global revocation in Nostr. The spec MUST state this plainly in user-facing copy rather than implying otherwise.

## 4. Data layer

All state is Nostr events. **No SQL or NoSQL store holds user content.** Nodes MAY cache events, and any cache MUST be reconstructible from relays.

### 4.1 Event kind register

| Purpose | Kind | NIP | Notes |
|---|---|---|---|
| Profile metadata | `0` | NIP-01 | Carries NIP-39 `i` tags |
| Relay list | `10002` | NIP-65 | Outbox model; MUST be published at enrolment |
| App state / settings | `30078` | NIP-78 | Addressable, `d`-tag namespaced |
| Comments & threads | `1111` | NIP-22 | **NOT kind 1.** v1 specified kind 1 for comments; that pollutes global feeds |
| Long-form content | `30023` | NIP-23 | Node-authored articles |
| Private payloads (encryption primitive) | — | **NIP-44 v2** | **NIP-04 is deprecated and MUST NOT be used** |
| Direct messages | `1059` gift wrap | NIP-17 | NIP-04 DMs are deprecated in favour of NIP-17 |
| Curated lists / follow sets | `30000` | NIP-51 | App allowlists. Kind `30001` (generic lists) is deprecated — MUST NOT be used |
| Deletion request | `5` | NIP-09 | Advisory only — MUST be described as such |

### 4.2 Profile — kind 0

```json
{
  "kind": 0,
  "pubkey": "<pubkey_hex>",
  "content": "{\"name\":\"dorian\",\"display_name\":\"Dorian\",\"about\":\"Building Berm.\",\"picture\":\"https://…\",\"nip05\":\"_@xonly.ai\",\"website\":\"https://xonly.ai\"}",
  "tags": [
    ["i", "twitter:dorian_handle", "1789456123456789012"],
    ["i", "github:dorian", "9721ce4ee4fceb91c9711ca2a6c9a5ab"]
  ],
  "created_at": 1785000000
}
```

`content` is a JSON **string**, not an object. Clients that emit an object are non-conforming.

### 4.3 App state — kind 30078

```json
{
  "kind": 30078,
  "pubkey": "<pubkey_hex>",
  "content": "<NIP-44 v2 ciphertext, self-encrypted>",
  "tags": [
    ["d", "berm:settings:v2"]
  ],
  "created_at": 1785000060
}
```

Normative: `d` tags **MUST** use the `berm:<namespace>:<version>` form so that independently built mini-apps cannot collide. Any state that is not intended to be world-readable **MUST** be NIP-44-encrypted to the user's own pubkey. v1's plaintext `{"theme":"dark","allowed_apps":[…]}` leaks the user's full app graph to every relay operator — corrected here.

### 4.4 Relay policy

- Nodes **MUST** publish to the union of the user's kind 10002 write relays and the node's configured defaults.
- Nodes **MUST NOT** hardcode a single relay. Minimum three, from at least two independent operators.
- Publish is considered successful on **≥2 distinct relay OKs**, not one.
- Read path **MUST** implement the NIP-65 outbox model, not a fixed relay list.

### 4.5 Encryption

NIP-44 v2 (ChaCha20 + HMAC-SHA256, versioned padding). NIP-04 is deprecated, leaks message length, and lacks authentication; it is **prohibited** in this codebase, including in examples and tests.

## 5. Node architecture — `xonly-node` (WordPress plugin)

> **Naming note (§9.2):** v1's `x-sovereign-everything-bridge` plus a stated goal of cloning X's visual design is a trademark exposure independent of any TOS question. The plugin slug, the UI kit, and all marketing copy are renamed away from X trade dress in v2.

### 5.1 Trust boundary

```
┌─ NODE (untrusted) ─────────────────────────────┐   ┌─ SIGNER ORIGIN ─────────┐
│                                                │   │                         │
│  PHP                     Browser JS            │   │  WebAuthn + PRF         │
│  ├ OAuth 2.0 + PKCE  →   ├ window.berm SDK ────┼───┼→ NIP-46 handler         │
│  ├ /2/users/me           ├ event composition   │   │  ├ derive sk            │
│  ├ NIP-39 verify         ├ relay pub/sub       │   │  ├ sign event           │
│  └ render                └ receives SIGNATURES │   │  └ nip44 encrypt/decrypt│
│                                                │   │                         │
│  ✗ never sees: sk, prf_out, nsec               │   │  ✗ never transmits: sk  │
└────────────────────────────────────────────────┘   └─────────────────────────┘
```

### 5.2 PHP responsibilities (exhaustive — anything else is a bug)

1. Serve the OAuth 2.0 + PKCE handshake.
2. Call `/2/users/me` once; extract handle + ID; discard the token.
3. Verify the NIP-39 claim (Channel B) and expose the result to the frontend as a boolean.
4. Store node configuration (relay defaults, signer origin, app registry).
5. Enqueue scripts with Subresource Integrity and render shortcodes/blocks.

**Prohibited in PHP:** touching key material; persisting raw X user IDs; writing user content to `wp_posts`/`wp_users`/`wp_usermeta` as a source of truth; signing anything; proxying relay traffic in a way that hides which relays were used.

### 5.4 SDK surface — `window.berm` (normative)

Every method routes through the active signer tier. **No method returns or accepts a private key.**

```ts
interface Berm {
  readonly version: '2.0.0';

  /** Resolve the active tier. Never silently downgrades. */
  connect(opts?: { preferred?: 0 | 1 | 2 }): Promise<Session>;

  /** Current identity. Public data only. */
  getPublicKey(): Promise<string>;                         // hex
  getNpub(): Promise<string>;

  /** Signing. Returns a complete, signed, verifiable event. */
  signEvent(template: EventTemplate): Promise<SignedEvent>;

  /** NIP-44 v2 only. */
  encrypt(peerPubkey: string, plaintext: string): Promise<string>;
  decrypt(peerPubkey: string, ciphertext: string): Promise<string>;

  /** Relay I/O with outbox-model routing. Resolves on >= 2 OKs. */
  publish(event: SignedEvent, relays?: string[]): Promise<PublishReceipt>;
  query(filters: Filter[], relays?: string[]): AsyncIterable<SignedEvent>;

  /** X binding state for the current session. Read-only. */
  readonly binding: { state: 'verified' | 'claimed' | 'unlinked'; handle?: string };
}
```

Mini-apps built by third parties (human or AI) target **only** this interface. That is what makes downstream generation deterministic: the surface is fixed, the security properties are enforced below it, and a mini-app author cannot reach key material even by accident.

### 5.5 Mini-app agent contract

Replaces v1's `/.github/prompts/mini-app-agent.prompt`. Rules 1 and 2 survive; the rest are rewritten.

```
You are a mini-app author for Berm v2. Hard constraints:

1. No centralized SQL/NoSQL persistence. All state is Nostr events.
2. All reads/writes go through `window.berm`. Never import a signing library,
   never construct a key, never call getPublicKey on anything but window.berm.
3. Any state not intended to be world-readable MUST be written via
   window.berm.encrypt (NIP-44 v2). Never NIP-04.
4. Addressable events MUST use a `d` tag of the form `berm:<app-slug>:<version>`.
5. Comments and threads use kind 1111 (NIP-22). Never kind 1.
6. Never render an identity as verified unless session.binding.state === 'verified'.
7. UI inherits the Berm neutral design system. Do not replicate X trade dress:
   no X logo, no X colour tokens, no X typography, no "X" in the app name.
8. Every network endpoint you touch must be declarable in a static allowlist.
   Dynamic endpoint construction is rejected at review.
```

## 6. Verifiability and supply chain

Non-negotiable, because Tier 1 asks users to trust served bytes.

1. **Reproducible builds.** `reproducible-build.yml` builds in a pinned container from `SOURCES.lock` and asserts byte-identical output against the release artifact. A non-reproducing release **MUST** be blocked, not shipped with a note.
2. **No CDN.** All scripts are served from the node or signer origin with SRI `sha384` hashes injected from `build/manifest.json`. Zero third-party script origins.
3. **Signed releases.** Every tag signed by ≥2 of N maintainer keys. The signing pubkeys are published in `.well-known/nostr.json` and in the repo.
4. **Publish the hashes to Nostr.** Each release emits a kind 1 (announcement) and a kind 30078 with `d = berm:release:<version>` carrying the manifest hash, signed by the project key. A user can verify what they're running without trusting GitHub.
5. **Client-side auditability.** The signing path MUST be observable: a user opening devtools MUST be able to confirm that no request carrying key material leaves the signer origin. CSP `connect-src` is restricted to WSS relay endpoints; violations are reported.
6. **Human gate.** No AI-generated change to `/includes/class-oauth-pkce.php`, the signer, or any file under a `crypto/` path is auto-mergeable. Two human maintainer approvals required. AI agents MAY author, MUST NOT approve.

## 7. Test vectors (required before any downstream work)

Downstream is only deterministic if the primitives are pinned. `crypto/test-vectors.json` **MUST** exist and CI **MUST** assert it.

| Vector | Asserts |
|---|---|
| `prf_out` (fixed 32B) → `sk`, `pubkey`, `npub`, `nsec` | Derivation stability across browsers and rebuilds |
| `prf_out` engineered to produce `sk ≥ n` at `i=0` | Counter retry path is exercised, not dead code |
| kind 0 with two `i` tags → canonical serialization → `id` | NIP-01 event ID computation |
| NIP-44 v2 round trip against the official vector file | Correct cipher, correct padding |
| Same passkey, two origins | **MUST fail** — proves RP-ID scoping is real and Tier 1 centralisation is necessary |
| v1 derivation applied to a known X ID | **MUST be flagged** — a regression guard so the broken primitive can never re-enter |

## 8. Failure modes

### 8.1 X account banned or OAuth revoked

Impact: the login button and Channel B attestation stop working. **No key is lost, no data is lost, no identity changes.**

```ts
async function authenticate(): Promise<Session> {
  if (window.nostr) return sessionFromNip07();                    // Tier 0
  try   { return await sessionFromXnsbSigner(); }                 // Tier 1
  catch (e) {
    if (e instanceof PrfUnsupportedError) return await sessionFromNip46();  // Tier 2
    throw e;
  }
}
// X OAuth is invoked separately, for display + attestation only.
// It is NEVER on this path. Its failure degrades a badge, not a login.
```

Note the inversion from v1: there, X failure meant *no key*. Here, X failure means *no badge*.

### 8.2 Signer origin unavailable

Users hold their backup from §3.2.3. Any NIP-46 bunker or NIP-07 extension imports it. Documented in-product, not only in docs. The signer is **replaceable infrastructure**, by construction.

### 8.3 Domain loss (xonly.ai)

NIP-05 breaks; identities do not. Project announcements continue on Nostr under the project key, which is published in the repo, in every release event, and in the plugin binary. Users verify the project key from any of three independent paths.

### 8.4 Relay loss

NIP-65 outbox routing plus the ≥2-relay publish rule. A user MAY add relays at any time; historical events propagate on re-broadcast.

## 10. Treasury and contributor rewards

Architecturally decoupled — it touches no identity path. Specified here only to fix the interface.

- Trading fees accrue off-platform to a multisig treasury.
- Payout trigger: PR merged to `main` **after** two human maintainer approvals. AI-authored PRs are eligible; AI approvals are not.
- Payout address resolution: contributor publishes a kind 30078 with `d = berm:payout:v1` containing their chain address, signed by their Berm identity. The GitHub↔Nostr link is a NIP-39 `github:` claim (gist proof). **The payout oracle MUST NOT accept an address supplied in the PR body.**
- Contract address is published on xonly.ai, in the repo README, and in a signed Nostr event under the project key. Three independent verification paths, none of them an X post.
- Anti-farming: reward weight is set by maintainer review at merge time, not by diff size, commit count, or line count.

**Sequencing constraint:** the token launches **after** §7 test vectors pass and an external review of §3 completes. Launching a token on top of an unreviewed identity layer converts an engineering project into a target.

## 11. Conformance checklist

An implementation is Berm v2 conformant iff all of the following hold.

- [ ] No code path derives key material from an X user ID, handle, or any public identifier.
- [ ] All key derivation input originates from CSPRNG or WebAuthn PRF.
- [ ] secp256k1 scalar validity is checked with counter-based retry.
- [ ] Node PHP never receives `sk`, `nsec`, or `prf_out`.
- [ ] Raw X user IDs are not persisted anywhere.
- [ ] X↔npub binding uses NIP-39 `i` tags; no custom identity tag exists.
- [ ] `.well-known/nostr.json` is served at the correct path, with `_` as the bare-domain name, with CORS.
- [ ] Comments use kind 1111; kind 1 is not used for threaded replies.
- [ ] All private payloads use NIP-44 v2; NIP-04 appears nowhere, including tests.
- [ ] Addressable events use `berm:<namespace>:<version>` `d` tags.
- [ ] Publish requires ≥2 relay OKs across ≥2 operators.
- [ ] Enrolment blocks until a verified backup exists.
- [ ] Tiers 0 and 2 are reachable and tested; Tier 1 is not required for any operation.
- [ ] No end-user-facing copy calls Tier 1 sovereign, self-custodial or trustless (§3.2.5.1).
- [ ] The T9 disclosure of §3.2.5 is present in the user-facing custody documentation, not only in the spec.
- [ ] The signer origin's registration expiry is published, and the build-attestation key is held offline and off the web server.
- [ ] Releases are reproducible, SRI-pinned, multi-sig signed, and hash-announced on Nostr.
- [ ] Test vectors in §7 pass, including the two negative vectors.
- [ ] No X trade dress in code, assets, or copy.

## 12. Rejected alternatives

### 12.1 v1: `nsec = HKDF(x_user_id, public_salt)` — **rejected, unsalvageable**
Zero-bit security (§0). Every proposed patch fails: adding a PIN yields offline brute-force against a known npub; per-site salting destroys the cross-site property that motivates the design; server-held pepper reintroduces the centralized custodian the project exists to eliminate.

### 12.2 Per-site passkey, no central signer — **rejected**
RP-ID scoping yields a different identity per domain (§3.2.1). Fails the core requirement.

### 12.3 Password/passphrase-derived key (Argon2id) — **rejected as default, retained as backup format only**
Works cross-origin and cross-device, but a memorized passphrase is the sole factor, unrotatable, and offline-attackable once the npub is public. Acceptable for an encrypted backup file (§3.2.3), not for primary custody.

### 12.4 Custodial keys with X login — **rejected**
Simplest UX, but the custodian can sign as any user, which is v1's failure mode with a different owner. Contradicts axiom 3.

### 12.5 Node-side signing proxy — **rejected**
Would let mini-apps skip the signer round-trip, at the cost of every node operator becoming a signing oracle. Contradicts axiom 3.
